# Advanced SELECT and Filtering — Foundation Notes

## Why do we need this?

Imagine you have a million orders but the business asks: **Which paid orders exceeded ₹1,000 this month?** SQL's job is to choose the correct **rows**, **columns**, and **order**. Begin by describing what a single result row represents.

## 1. Example dataset — one row per order

| order_id | customer_id | status | amount |
|---:|---:|---|---:|
| 101 | 1 | paid | 1200 |
| 102 | 2 | pending | 2000 |
| 103 | 1 | paid | 800 |
| 104 | 3 | paid | 1500 |

## 2. Build the query visually

```text
Orders (4 rows)
    ↓ WHERE status = 'paid' AND amount > 1000
Orders 101, 104 (2 rows)
    ↓ SELECT order_id, customer_id, amount
Three columns (2 rows)
    ↓ ORDER BY amount DESC
104 → 101
```

```sql
SELECT order_id, customer_id, amount
FROM Orders
WHERE status = 'paid' AND amount > 1000
ORDER BY amount DESC, order_id;
```

**Result**

| order_id | customer_id | amount |
|---:|---:|---:|
| 104 | 3 | 1500 |
| 101 | 1 | 1200 |

Read it from the data: 102 is pending; 103 is paid but too small. Both fail the filter.

## 3. Essential filters

| SQL | Meaning |
|---|---|
| `WHERE city IN ('Pune','Mumbai')` | Matches either listed city |
| `WHERE amount BETWEEN 100 AND 500` | Includes both endpoints |
| `WHERE name LIKE 'A%'` | Starts with A (case rules depend on dialect/collation) |
| `WHERE city IS NULL` | Missing city; never use `= NULL` |
| `SELECT DISTINCT city` | Unique projected values |
| `CASE WHEN amount >= 1000 THEN 'High' ELSE 'Low' END` | Output label |

**SQL Server versus SQLite:** SQLite uses `LIMIT 5` after sorting; SQL Server uses `TOP (5)` in SELECT (or `OFFSET … FETCH`). Use explicit `ORDER BY` for deterministic top results.

## 4. SQL reasoning order

`FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/TOP` is a useful *logical reasoning* model, not necessarily the database's physical execution plan.

**JS analogy:** `orders.filter(...).map(...).sort(...)` resembles the **purpose** of SQL filtering, projection and sorting, but SQL has different `NULL`/type semantics and the engine may optimize execution.


## Source-specific checks: prices, metro aliases and discount ties

The [PNP SELECT statement audit](../PNP-SEMANTIC-AUDIT.md) inspected P002/P003/P005/P007/P008 separately. These are teaching clarifications from those requirements, not newly submitted learner answers.

**Fixed top-N versus including ties (P002).** A ten-slot display needs exactly ten non-NULL priced rows with a secondary ProductID order. RANK/DENSE_RANK with ties can return **more** than ten rows, while LIMIT without a deterministic tie-break can choose different equal-priced products on successive executions.

**Normalize for matching, preserve display intent (P003).** A test of LOWER(TRIM(city)) can match Bengaluru/Bangalore, Mumbai/Bombay and Delhi/New Delhi. Sorting by LOWER(TRIM(city)) is *not identical* to ordering by TRIM(city) under case-sensitive collations; decide whether the business wants normalized or literal display sort before choosing.

**Quarter timestamp boundary (P005).** Prefer a half-open time interval for Q1: greater than or equal to January 1 and strictly earlier than April 1. Filtering through March 31 as a bare date string can exclude March 31 records that include an hours/minutes component.

**Safe discount and deterministic ties (P007).** A source market price of 0 or NULL should produce a NULL rupee discount **and** NULL percentage without discarding the product. An illustrative, reviewer-authored SQLite pattern:

```sql
SELECT ProductID,
       NULLIF(Market_Price, 0) - Sale_Price AS rupee_discount,
       ROUND(100.0 * (Market_Price - Sale_Price) /
             NULLIF(Market_Price, 0), 2) AS discount_pct
FROM Products
ORDER BY discount_pct DESC, ProductID ASC;
```

Both expressions now yield NULL for Market_Price = 0 or NULL, even if Sale_Price is nonzero. Keep the product row, but distinguish unavailable discount from zero discount. Dialect-specific NULL sorting and typed numeric arithmetic still require source-target checks.

**Price bands (P008).** Ordered CASE branches must put a value of 200 in Mid, a value of 699.50 in Mid, a value of 700 in Premium and a NULL in Unknown. Do not use an inclusive BETWEEN 200 AND 700 if 700 starts Premium.

## Quick revision

- `WHERE` filters input rows; `CASE` labels output values.
- Always specify the final row grain and tie-breaking order.
- `DISTINCT` applies to the combination of selected columns, not merely one field when multiple columns are projected.
- `UNION` removes duplicate rows, `UNION ALL` retains them; columns must be compatible.
- Avoid `SELECT *` in production-facing reports.
