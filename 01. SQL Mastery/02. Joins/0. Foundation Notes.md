# SQL Joins — Foundation Notes

## Why learn joins?

An e-commerce database stores customers and orders separately to avoid repeating all customer details inside every order. A **join** combines related rows using their shared key.

## 1. Example input

**Customers**

| CustomerID | Name |
|---:|---|
| 1 | Asha |
| 2 | Ravi |
| 3 | Neha |

**Orders**

| OrderID | CustomerID |
|---:|---:|
| 201 | 1 |
| 202 | 1 |
| 203 | 3 |

## 2. INNER JOIN — matching rows only

```sql
SELECT c.CustomerID, c.Name, o.OrderID
FROM Customers c
INNER JOIN Orders o ON c.CustomerID = o.CustomerID
ORDER BY c.CustomerID, o.OrderID;
```

**Output**

| CustomerID | Name | OrderID |
|---:|---|---:|
| 1 | Asha | 201 |
| 1 | Asha | 202 |
| 3 | Neha | 203 |

Asha has **two orders**, so the join creates **two rows**. Joins can multiply rows; they aren't always one customer → one result.

## 3. LEFT JOIN — keep unmatched customers

Change `INNER JOIN` to `LEFT JOIN`.

| CustomerID | Name | OrderID |
|---:|---|---:|
| 1 | Asha | 201 |
| 1 | Asha | 202 |
| 2 | Ravi | NULL |
| 3 | Neha | 203 |

Ravi remains even though no order matches.

## 4. Anti-join — customers with no orders

```sql
SELECT c.CustomerID, c.Name
FROM Customers c
LEFT JOIN Orders o ON c.CustomerID = o.CustomerID
WHERE o.OrderID IS NULL;
```

**Output:** `(2, Ravi)`. Test a **non-null right-side key** for missing matches, not an arbitrary nullable attribute.

## 5. ON vs WHERE is crucial

To attach **only paid orders** while keeping every customer, put the qualifying `status='paid'` condition in the `LEFT JOIN ... ON` clause. Putting `WHERE o.status='paid'` afterwards filters out unmatched customers.

**Step-by-step mental model:** choose left rows → find qualifying right matches → fill missing right columns with NULL → apply final WHERE.

## 6. Types and cautions

- `INNER JOIN`: only matches; `LEFT JOIN`: all left rows plus matches.
- `RIGHT JOIN` and `FULL OUTER JOIN` are also available in supported SQL dialects; SQLite version support varies, so test the actual engine.
- SQL is a multiset language: duplicates and join fan-out affect counts and sums.
- Always identify table **grain** before joining; aggregating after a one-to-many join can double-count.
- Sort explicitly; joins do not guarantee output ordering.

**JS developer connection:** A join resembles building a lookup `Map` keyed by customer ID and attaching matching orders, but SQL can produce multiple rows per key and has NULL semantics.

## 7. Four source-backed join patterns worth practicing

These are **teaching patterns**, not submitted solutions to the unsolved PNP exercises. The [source-specific inspection register](../PNP-SEMANTIC-AUDIT.md) records the exact question IDs and which isolated tests passed.

### A. Full outer emulation when a dialect lacks FULL JOIN (A006)

Think of it as *every left row plus right-only rows*. A left join already contains the matched rows; adding **all** rows from the other side would duplicate those matches. Use a `UNION ALL` with the right-only part filtered by a **non-nullable left key**. In the example, customers (1, Asha) and (2, Mira) with orders (10, customer 1) and (11, customer 3) produce (Asha, 10), (Mira, NULL), and (NULL, 11). A truly missing `orders.cust_id` must also survive.

### B. Don't sum money after multiplying order rows (P029)

Suppose order 10 costs ₹100 and has two lines, of 2 and 3 units; order 11 costs ₹200 with 4 units. A direct `Orders JOIN OrderDetails` has **three rows** and naively computes ₹100 + ₹100 + ₹200 = **₹400**. The correct order-level money is **₹300**, while units total **9**.

**Intermediate grains:**

| Stage | Key / grain | What it stores |
|---|---|---|
| Orders | one row per order | order 10 → ₹100; order 11 → ₹200 |
| OrderDetails | one row per line | order 10 → 2 units and 3 units; order 11 → 4 units |
| Line summary | one row per order | order 10 → 5 units; order 11 → 4 units |
| Final reporting | one row per shipper | two orders, ₹300 and 9 units |

**Recipe:** aggregate line quantities by `OrderID` first, then attach that one-row-per-order summary to Orders before calculating any shipper-level totals. Use a left join if orders without detail lines should still count. `SUM(DISTINCT Total_Order_Amount)` is **not** a fix: different orders can have the same amount.

### C. Count *products*, not line items, in category coverage (P039)

A category containing one product sold on three separate lines still has **one sold product**. First make per-product totals; then join Products to Category, retaining categories with zero products. Separate `COUNT(product_id)` from the number of products whose aggregated line count is nonzero; use `COALESCE` for zero units. This distinguishes *No products*, *Products but no sales*, *Some products unsold*, and *All products sold*.

### D. Treat unordered pairs and repetitions correctly (A011 / P070)

For employee colleague pairs, self-join the department table with `left.emp_id < right.emp_id`; this removes (A,A) and the mirrored (B,A) of (A,B). For co-purchased subcategories, first deduplicate **(OrderID, Sub_Category)**. Then make pairs using an alphabetical comparison `subcategory_a < subcategory_b` and count orders. Deduplication prevents multiple Tea products or repeated Tea lines within a single order from inflating the Tea–Snacks count. For a *top ten including all ties at tenth place* contract, distinguish `RANK() <= 10` (rank gaps retained) from `ROW_NUMBER() <= 10` (arbitrarily truncates ties).

**Related traps:** a date × category cross join needs distinct dates/categories and a defined date dimension (A008); non-equi price-band joins need boundaries that do **not overlap** (A009); “bought 101 but never 202” is a customer-level anti-join spanning **all orders** (A013). For signup conversion, calculate the **first** order date before applying a 0–30-day eligibility check, and keep nonbuyers in the denominator (P053).
