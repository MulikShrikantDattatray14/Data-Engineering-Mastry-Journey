# SQL Aggregation — Foundation Notes

## Why do we need this?

Data engineers convert millions of event rows into metrics such as revenue, daily active customers, success rate, and average order value. Aggregation combines many rows into a **summary**.

## 1. Input data

| id | status | amount |
|---:|---|---:|
| 1 | paid | 100 |
| 2 | paid | 200 |
| 3 | failed | 50 |
| 4 | paid | NULL |

## 2. Understand what each function counts

```sql
SELECT
  COUNT(*) AS rows_seen,
  COUNT(amount) AS known_amounts,
  SUM(amount) AS amount_total,
  AVG(1.0 * amount) AS mean_known_amount
FROM Transactions;
```

| rows_seen | known_amounts | amount_total | mean_known_amount |
|---:|---:|---:|---:|
| 4 | 3 | 350 | 116.67 (approx.) |

```text
COUNT(*)          4 rows
COUNT(amount)     3 non-NULL values
SUM(amount)       100 + 200 + 50 = 350
AVG(amount)       350 / 3 ≈ 116.67
```

**Why:** SQL aggregates such as `SUM`, `AVG` and `COUNT(column)` ignore `NULL` inputs. `COUNT(*)` counts rows regardless of NULL. If no non-NULL amounts exist, `SUM(amount)` is NULL, not zero.

## 3. Conditional aggregation

```sql
SELECT
  SUM(CASE WHEN status='paid' THEN 1 ELSE 0 END) AS paid_count,
  SUM(CASE WHEN status='paid' THEN amount ELSE 0 END) AS paid_amount
FROM Transactions;
```

| paid_count | paid_amount |
|---:|---:|
| 3 | 300 |

Even with unknown amount for a paid row, it still contributes **one** to the count; its NULL amount does not contribute money.

## 4. Ratios and safe division

```sql
SELECT
  100.0 * SUM(CASE WHEN status='paid' THEN 1 ELSE 0 END)
  / NULLIF(COUNT(*), 0) AS paid_pct
FROM Transactions;
```

**Result:** 75.0. Multiplying by `100.0` avoids integer truncation in SQLite. `NULLIF(x,0)` makes a zero denominator NULL rather than dividing by zero.

## 5. Join fan-out warning

If one order has three order-item rows, joining Orders to Items produces **three joined rows** for that order. Summing the **order-level** total *after* that join counts it three times. Aggregate items to order grain first, or compute the desired metric from a grain-appropriate table.

**JS analogy:** Think `reduce()` over an array, but identify the units being reduced and whether the array was duplicated by a join.

## 6. Source-aligned aggregation edge cases (reviewed question texts, not solved exercises)

The archived PNP [question index](../PNP-PROBLEM-INDEX.md) exposes different **grains** that must be chosen before writing any GROUP BY:

- **P011:** A Products LEFT JOIN OrderDetails has one row for every unsold product too. Count joined rows, matched sale lines, listed products and sold products separately; a dangling OrderDetails product ID cannot become a listed product.
- **P047:** To decide if a brand lists at least three products, count catalogue products **before** multiplying rows through sales lines. Aggregate units per ProductID first and retain unsold products with zero units.
- **P051:** COUNT(DISTINCT SupplierID) ignores NULL. An order with only NULL supplier references has *zero known suppliers*; an order with one known supplier and other NULL lines is still a one-known-supplier order, although the unknown lines deserve a data-quality flag.
- **P054:** A plain average of product-level discounts includes eligible unsold products. A unit-weighted discount uses SUM(discount_pct × units) / SUM(units) **after** rolling lines to one row per product. A product with no valid Market_Price is excluded from both; a group with zero sold units has an undefined weighted average (NULL), not 0%.
- **P059:** Calculate each order's basket totals and distinct products first. An order with no lines is outside the denominator; taking AVG over joined line rows biases the result toward larger baskets.
- **P084:** A state subtotal and grand total must be calculated from underlying delivered orders (or weighted sums/counts), **never** from an unweighted average of shipper averages. Apply the minimum-five-order display rule independently at each output grain; label subtotal rows explicitly so a missing state is not confused with the grand total.
- **P035/P052:** Date-based courier metrics must separate valid delivery sequences, missing dates and invalid date order; decide which orders enter the denominator before calculating a percentage or mean.
- **A026:** The archived advanced *unpivot* question refers to a cust_summary table absent from its shared base schema. It requires that extra input and cannot be certified against an unavailable source dataset.

**Runnable SQLite illustration: plain vs unit-weighted discount**

```sql
WITH products(discount_pct, units) AS (
  VALUES (10.0, 1), (50.0, 3), (20.0, 0)
)
SELECT ROUND(AVG(discount_pct), 2) AS simple_pct,
       ROUND(SUM(discount_pct * units) / NULLIF(SUM(units), 0), 2) AS weighted_pct,
       SUM(units) AS total_units
FROM products;
```

| simple_pct | weighted_pct | total_units |
|---:|---:|---:|
| 26.67 | 40.00 | 4 |

Intermediate reasoning: the 20%-discount product is eligible for the simple average but has **zero units**, so the simple mean is (10+50+20)/3 = 26.67%. The unit-weighted rate is (10×1+50×3+20×0)/4 = 40%. The example is auditor-written and was executed in SQLite; it is **not** a saved learner or official answer.

## Quick revision

- `COUNT(*)` ≠ `COUNT(column)` when NULL exists.
- Decide whether `NULL` means unknown before replacing it with zero.
- Weighted average = `SUM(value * weight) / SUM(weight)`, **not** average of group averages.
- Separate original row grain, business metric grain, and grouping key.
