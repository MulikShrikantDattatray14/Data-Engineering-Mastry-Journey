# Common Table Expressions (CTEs) — Foundation Notes

## Why do we need this?

A long SQL query gets hard to debug when filtering, grouping and ranking happen in one expression. A **CTE** names an intermediate result so you can build the answer in understandable stages.

Think: **one small correct step → next correct step → final result**.

## 1. Business case

Find customers with at least ₹300 of paid sales.

**Orders**

| order_id | customer_id | status | amount |
|---:|---:|---|---:|
| 1 | 10 | paid | 100 |
| 2 | 10 | paid | 250 |
| 3 | 20 | failed | 500 |
| 4 | 20 | paid | 50 |

## 2. Visual flow

```text
Orders
  ↓ CTE paid_orders
(10,100), (10,250), (20,50)
  ↓ CTE customer_totals
(10,350), (20,50)
  ↓ final WHERE total >= 300
(10,350)
```

```sql
WITH paid_orders AS (
  SELECT customer_id, amount
  FROM Orders
  WHERE status = 'paid'
),
customer_totals AS (
  SELECT customer_id, SUM(amount) AS total
  FROM paid_orders
  GROUP BY customer_id
)
SELECT customer_id, total
FROM customer_totals
WHERE total >= 300
ORDER BY total DESC, customer_id;
```

**Final output**

| customer_id | total |
|---:|---:|
| 10 | 350 |

## 3. What to remember

- A CTE starts with `WITH name AS (SELECT ...)`.
- Multiple CTEs are separated by commas and can refer to earlier CTEs.
- The named result is available to its containing statement; it isn't automatically a persistent stored table.
- A CTE does **not** guarantee better performance: the query planner decides how to execute it.
- Recursive CTEs repeatedly derive rows; those have a separate foundation note.

**JS analogy:** Like naming intermediate transformations in variables for readability, but a SQL CTE is not literally a materialized JS array; the optimizer may inline or reevaluate it.

## Debugging strategy

Temporarily change the final SELECT to `SELECT * FROM paid_orders` or `customer_totals` to inspect each stage. Validate expected *row count* and *grain* before continuing.
