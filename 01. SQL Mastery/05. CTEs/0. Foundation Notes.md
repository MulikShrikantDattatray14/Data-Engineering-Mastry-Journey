# Common Table Expressions (CTEs) — Foundation Notes

## Why do we need this?

A long SQL query gets hard to debug when filtering, grouping and ranking happen in one expression. A **CTE** names an intermediate result so you can build the answer in understandable stages.

Think: **one small correct step → next correct step → final result**.

## 1. Business case

Find customers with at least ₹300 of paid sales.

**Orders**

| order_id | customer_id | status | amount |
|---:|---:|---|---:|
| 1 | 10 | paid | 100 |
| 2 | 10 | paid | 250 |
| 3 | 20 | failed | 500 |
| 4 | 20 | paid | 50 |

## 2. Visual flow

```text
Orders
  ↓ CTE paid_orders
(10,100), (10,250), (20,50)
  ↓ CTE customer_totals
(10,350), (20,50)
  ↓ final WHERE total >= 300
(10,350)
```

```sql
WITH paid_orders AS (
  SELECT customer_id, amount
  FROM Orders
  WHERE status = 'paid'
),
customer_totals AS (
  SELECT customer_id, SUM(amount) AS total
  FROM paid_orders
  GROUP BY customer_id
)
SELECT customer_id, total
FROM customer_totals
WHERE total >= 300
ORDER BY total DESC, customer_id;
```

**Final output**

| customer_id | total |
|---:|---:|
| 10 | 350 |

## 3. What to remember

- A CTE starts with `WITH name AS (SELECT ...)`.
- Multiple CTEs are separated by commas and can refer to earlier CTEs.
- The named result is available to its containing statement; it isn't automatically a persistent stored table.
- A CTE does **not** guarantee better performance: the query planner decides how to execute it.
- Recursive CTEs repeatedly derive rows; those have a separate foundation note.

**JS analogy:** Like naming intermediate transformations in variables for readability, but a SQL CTE is not literally a materialized JS array; the optimizer may inline or reevaluate it.

## Debugging strategy

Temporarily change the final SELECT to `SELECT * FROM paid_orders` or `customer_totals` to inspect each stage. Validate expected *row count* and *grain* before continuing.

## Source-aligned edge cases (PNP A040–A045, P030)

### A042 — company mean is **not** a mean of department means

**Why:** When one department has more employees than another, averaging department averages gives each department equal weight, not each employee. The business wants the employee-level company average.

| Employee | Department | Salary |
|---|---:|---:|
| 1 | 10 | 50 |
| 2 | 10 | 70 |
| 3 | 20 | 120 |

- Department means: 60 and 120.
- Incorrect unweighted average of department means: (60 + 120) / 2 = **90**.
- Correct company mean across all three employees: (50 + 70 + 120) / 3 = **80**.

A **locally executed reviewer fixture** computes each department mean and separately computes the employee-wide mean. Missing-salary and nonmatching-department policies still need the source's full dataset.

### A043 — a window result must be filtered **outside** the window SELECT

A rank is calculated **after** filtering input rows. An alias assigned in the same SELECT is not available to that SELECT's WHERE clause. First calculate the rank in a CTE, then filter its results.

```sql
WITH ranked AS (
  SELECT emp_id, emp_name,
         RANK() OVER (ORDER BY salary DESC) AS r
  FROM employees
)
SELECT emp_name, r
FROM ranked
WHERE r <= 2
ORDER BY r, emp_id;
```

Executed example inputs (salary): Ada=90, Ben=90, Cora=80, Dee=70. The intermediate ranks are **1, 1, 3, 4**; the final rows are (Ada, 1), (Ben, 1). This is **RANK**, not ROW_NUMBER: the requested top *ranks* can include ties and return more than N records.

### A044 and A045 — the **grain** must survive each CTE

- **A044 order spine:** begin with one row per order; aggregate order_items to one count **per order** before LEFT JOIN. Use COALESCE(count,0) to keep orders with zero items. COUNT(item_id) counts *line rows*, not quantities.
- **A045 payment-event deduplication:** define the event key **before** removing duplicates. An illustrative archive example treats (order_id, paid_at) as an event key; it does **not** tell us how to settle different amounts recorded under that same key. Check an authoritative payment event identifier/contract before selecting a winner.
- **P030 retention:** use one row **per ordering customer** to label One-time or Repeat; then aggregate customer counts by label. Percentages divide by the number of *ordering customers*, not order rows, and the illustrated policy excludes NULL customer identifiers.
