# Subqueries — Foundation Notes

## Why do we need this?

Sometimes the answer depends on another answer: *Which employees earn more than their department's average?* A **subquery** computes something the outer query needs.

## Step 1: Look at the data

| employee_id | dept | salary |
|---:|---|---:|
| 1 | A | 100 |
| 2 | A | 200 |
| 3 | B | 300 |
| 4 | B | 500 |

Find employees above their own department's average.

## Step 2: Calculate the inner answer for each department

| dept | average_salary |
|---|---:|
| A | 150 |
| B | 400 |

For employee 1, the question is **100 > 150?** No. For 2: **200 > 150?** Yes. For 3: **300 > 400?** No. For 4: **500 > 400?** Yes.

## Step 3: Write a correlated subquery

```sql
SELECT e.employee_id, e.dept, e.salary
FROM Employees AS e
WHERE e.salary > (
  SELECT AVG(1.0 * x.salary)
  FROM Employees AS x
  WHERE x.dept = e.dept
)
ORDER BY e.employee_id;
```

**Result**

| employee_id | dept | salary |
|---:|---|---:|
| 2 | A | 200 |
| 4 | B | 500 |

The inner query **depends on the current outer employee's department**. This is correlation. The optimizer may execute it differently from a literal row-by-row loop.

## Four common inner-result shapes

| Shape | Common usage |
|---|---|
| One scalar value | `salary > (SELECT AVG(...))` |
| List of possible keys | `id IN (SELECT customer_id ...)` |
| A test of existence | `WHERE EXISTS (SELECT 1 ...)` |
| Derived table | `FROM (SELECT ...) AS summary` |

### Why NOT EXISTS is often safer than NOT IN

When the subquery contains a NULL, `x NOT IN (..., NULL)` can evaluate UNKNOWN rather than TRUE, unexpectedly excluding rows.

```sql
SELECT c.customer_id
FROM Customers AS c
WHERE NOT EXISTS (
  SELECT 1
  FROM Orders AS o
  WHERE o.customer_id = c.customer_id
);
```

This asks whether a matching row exists; it doesn't compare with an unknown list member.

**JS analogy:** For each item, use another dataset to decide inclusion, similar to `filter(employee => employee.salary > averageFor(employee.dept))`. SQL expresses the relationship rather than writing iteration.


## Source-aligned edge cases: semi-joins, relational division and scalar shares

These details arise from the independently *inspected source statements*, not from graded learner answers. The corresponding reviewer-only executable tests are in [the SubQueries regression runner](../../scripts/check_pnp_subqueries_cases.py); [the ID-level audit](../PNP-SEMANTIC-AUDIT.md) preserves every unanswered source problem's status.

### 1. One matching order versus many matching order lines

For A034, `EXISTS` or `IN` answers **which customers** have orders. A bare `JOIN` may generate one copy of a customer per order; use `DISTINCT` if that particular formulation is intended to return one row per customer. On a fixture with **two orders for customer 10**, all three semijoin formulations yielded exactly **one customer row**.

For A029, “latest order, **ties allowed**” means returning **every order whose date equals the maximum date for its customer**. On dates 2026-01-01, 2026-01-05 and 2026-01-05 for one customer, **both latter orders** qualify. This is the opposite of P058's explicitly single-order tie-break rule. Never silently swap one source's rule for another.

### 2. Quantifiers: ANY versus EVERY

A037 asks whether an order contains **any** Electronics product. A038 asks whether a customer has purchased **every** product from Audio; the second is *relational division*, not just a join to one matching row. A robust reasoning pattern is to search for **any required product with no purchase by this customer**. The customer qualifies only if such a missing product does **not exist** (nested `NOT EXISTS`).

In the independent synthetic check, customer 10 bought both Audio products, while customer 20 bought only one. **Only 10 qualified**. If Audio contains **zero products**, ordinary double-`NOT EXISTS` makes the “every” condition vacuously true for all catalogue customers. The original task does **not** specify whether to suppress those customers for an empty target category; mark that an unresolved source contract rather than manufacturing an official rule.

### 3. NULL anti-joins and set operators

A035's source intentionally demonstrates how `NOT IN (SELECT manager_id ...)` can return **no rows** when the inner result includes NULL, even when some employees manage nobody. Under the same synthetic rows, a correlated `NOT EXISTS` returned employees **2 and 3** correctly.

A007 specifically asks for a **set difference** of product IDs, plus an optional `NOT EXISTS` formulation for SQL versions lacking `EXCEPT`. With ordered-products IDs 1–4, order items referencing 1 and 3 (including one NULL), both formulations returned product IDs **2 and 4** in the reviewer SQLite fixture. `NOT EXISTS` avoids comparing an outer non-NULL product ID against a NULL inner list.

P057 is a related *set-operator* task stored under this section: it requires `UNION ALL`, retaining the same company under **both Supplier and Shipper roles**. A hypothetical de-duplicated company-name directory would violate the required grain.

### 4. “Top N salaries” can mean N rows or N distinct values

A078 prohibits windows and asks for the three top salaries per department. A correlated `COUNT(DISTINCT greater_salary)` models **top three distinct salary levels**, retaining salary ties. In the synthetic fixture, department 10 salaries `100,90,90,80,70` include **four employees** in the top three levels (`100,90,80`). The source's untied sample does **not** resolve whether “top 3” means three *employees* or three *salary levels*. This distinction must be confirmed before awarding official-answer verification.

### 5. Separate denominators and observation windows

P028's two percentages answer different questions: **order share = method's order count ÷ all order count**; **value share = method's total order amount ÷ all order amount**. Grouping must preserve unmatched or NULL PaymentID as Unknown. The reviewer fixture had two UPI and two Unknown orders, resulting in **50% each by count but 20% versus 80% by value**. In a production query, also define zero-denominator and an actual payment type literally named “Unknown.”

P056's latest calendar year is defined **from the data**, not the computer clock. Customers active in its previous calendar year but inactive in the latest year qualify, including those missing from the Customers dimension (show Unknown customer). The synthetic test deliberately included such an orphan ID.

P080's **90-day repeat-purchase rate** is a *cohort metric*: use each customer's **first** purchase date in the subcategory, require a **later calendar day** within 90 days for a repeat, and count only buyers observed for a full 90 days relative to **MAX(OrderDate)**. In the synthetic fixture, **30 eligible buyers and six qualified repeats** yielded **20.00%**; a second purchase on the same day, a later purchase beyond 90 days, and a recent ineligible buyer did not inflate the result. The source also requires **at least 30 eligible buyers** before returning a subcategory.

## Revision

- Distinguish `IN` (membership) and `EXISTS` (row existence).
- Correlation means a reference to the current outer row.
- Decide whether the inner query should return one value, one column or multiple columns.
- Always test empty results, NULL values and duplicates.
