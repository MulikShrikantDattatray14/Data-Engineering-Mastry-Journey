# Recursive CTEs — Foundation Notes

## Why do we need this?

An org chart can contain an unknown number of management levels. Hardcoding five self-joins won't work when depth changes. A **recursive CTE** repeatedly expands from known starting rows.

## 1. Visual mental model

```text
Start (anchor) → 1
                  ↓ add 1
Round 1       → 2
                  ↓ add 1
Round 2       → 3
                  ↓ add 1
Round 3       → 4
                  ↓ add 1
Round 4       → 5
                  ↓ stop
```

## 2. SQLite example

```sql
WITH RECURSIVE numbers(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1
  FROM numbers
  WHERE n < 5
)
SELECT n FROM numbers ORDER BY n;
```

**Progressive output**

| Iteration | Current n | Next n |
|---:|---:|---:|
| Anchor | — | 1 |
| 1 | 1 | 2 |
| 2 | 2 | 3 |
| 3 | 3 | 4 |
| 4 | 4 | 5 |
| 5 | 5 | None — stop |

Final output contains the integers **1, 2, 3, 4, 5**.

## 3. What makes it recursive?

A recursive CTE has an **anchor** query and a **recursive member** that reads from its own named result. Each round produces rows for the next round. A termination condition must ensure recursion eventually stops.

**SQL Server variant:** Use `WITH numbers(n) AS (...)` rather than `WITH RECURSIVE`. SQL Server has a default recursion depth limit and can use `OPTION (MAXRECURSION n)`; SQLite has different resource and recursion controls.

## 4. Real-world uses and warnings

- Employee hierarchy: start at CEO and follow manager-to-employee links.
- Tree navigation: folders, category relationships, dependency chains.
- Repeated date generation: build a calendar dimension for a range.
- **Cycle risk:** graph links such as A→B→A can loop. Use explicit depth bounds and/or path/cycle detection on graph-style data.

**JS analogy:** A queue-based BFS traversal starts from known nodes and processes newly discovered neighbors until the queue is empty. SQL recursion is declarative; engine behavior is not literally a JS call-stack recursion.

## Revision

Anchor → `UNION ALL` → recursive member → stop condition → final selection. Check ordering, cycles, deduplication, and the maximum intended depth.

## Source-backed hierarchy and splitting caveats (auditor note, 2026-11-09)

The preserved PNP Recursive CTE tasks A046–A050 were individually inspected and their illustrative contracts compared with **synthetic SQLite** cases in [the isolated regression script](../../scripts/check_pnp_recursive_streak_cases.py). This is **not learner mastery or MySQL official-answer verification**.

- **A046, calendar generation:** Anchor on 2026-01-01 and stop only *after* emitting 2026-01-31; expect exactly **31** rows, no table dependency. Inclusive end boundaries matter.
- **A047, manager 5 descendants:** Root is an *external manager*, so output begins at **level 1** with direct reports. Do not include manager 5 in that result. Sorting by level and employee ID yields deterministic output for the illustration.
- **A048, reporting paths:** A root-to-leaf traversal returns paths like `1 > 5 > 6`. A root-only walk **cannot claim to include every employee** if the input contains orphans or disconnected cycles. Specify how to report invalid organization components instead of silently losing them.
- **A049, org depth:** A root has depth **0**, so a chain of four employees has maximum depth **3**. Recursion depth caps are safety rails, not evidence that disconnected/cyclic data was successfully audited.
- **A050, splitting text:** A recursive splitter should maintain an ordinal for deterministic output: `a`, `b`, `c`. Consecutive separators, escaping and empty elements require an explicit source policy, which is missing.

**Cycle warning:** A recursive hierarchy without cycle detection or bounded depth may never terminate on cyclic links. An arbitrary depth cutoff avoids runaway evaluation but does not provide complete hierarchy semantics; cycle checks should use unambiguous token separators or a canonical visited set.
