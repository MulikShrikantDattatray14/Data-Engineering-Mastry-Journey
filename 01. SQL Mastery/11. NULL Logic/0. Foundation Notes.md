# SQL NULL and Full-Price Products — Foundation Notes

## Why this matters

An e-commerce promotion team needs products sold without a discount. A **known zero discount** is different from an **unknown discount** caused by missing prices. Mixing them produces incorrect business reports.

## What does NULL mean?

`NULL` indicates an unknown or missing value; it is not the text `'NULL'` and not the number 0. Use `IS NULL` or `IS NOT NULL` to check it.

| Market_Price | Sale_Price | Difference | Meaning |
|---:|---:|---:|---|
| 100 | 100 | 0 | Known full price |
| 100 | 90 | 10 | Known discount |
| 100 | NULL | NULL | Unknown; **not** verified full price |

```sql
SELECT ProductID, Sale_Price, Market_Price
FROM Products
WHERE Market_Price IS NOT NULL
  AND Sale_Price IS NOT NULL
  AND Market_Price = Sale_Price;
```

**Explanation:** Both prices must exist, then equality proves no discount.

## CASE displays; WHERE filters

```sql
SELECT ProductID,
       CASE WHEN Market_Price = Sale_Price
            THEN 'Full price'
       END AS discount_display
FROM Products
WHERE Market_Price IS NOT NULL
  AND Sale_Price IS NOT NULL
  AND Market_Price = Sale_Price;
```

- `CASE` labels the row.
- `WHERE` decides whether the row appears.
- `'NULL'` is a string. Actual SQL `NULL` is unquoted.

## Revision

- Remember three-valued logic: conditions involving `NULL` may evaluate to UNKNOWN.
- Compare prices only when both are known.
- SQLite accepts `==` for equality, but standard `=` is more portable.
- `ORDER BY Sale_Price DESC, ProductID ASC` makes tied prices deterministic.

## Source-aligned NULL pitfalls (PNP A091–A095 and P024)

### A091 and A095 — counts and averages have different denominators

| Expression | Counts or includes |
|---|---|
| COUNT(*) | Every input row, even when a value is missing |
| COUNT(manager_id) | Rows where manager_id is not NULL |
| COUNT(DISTINCT manager_id) | Unique non-NULL manager IDs |
| AVG(discount) | Mean across **non-NULL discounts** only |
| SUM(discount) / COUNT(*) | Uses **all rows** as denominator, including NULL discounts |
| SUM(discount) / NULLIF(COUNT(discount),0) | Matches the AVG denominator; watch integer division |

In reviewer-made test data: manager IDs (NULL, 1, 1, 2) yield counts **4 / 3 / 2**. Discounts (10, NULL, 20) yield AVG **15** versus SUM / COUNT(*) **10**. A095 names a discount column absent from its original seven-table source schema; this is an *illustrative* test, not an official dataset result.

### A092 — stable sorting with NULLs last

Never assume SQL dialects agree on default NULL ordering. A MySQL-compatible and SQLite-compatible explicit sort uses CASE; SQL Server also supports this form:

```sql
SELECT emp_id, salary
FROM employees
ORDER BY CASE WHEN salary IS NULL THEN 1 ELSE 0 END,
         salary DESC, emp_id ASC;
```

In a locally executed five-row check, salaries were 100, 100, 50, NULL, NULL; the final employee ID order was **2, 5, 3, 1, 4**. A tie-breaker on emp_id prevents unstable ordering.

### A093 — COALESCE chooses first non-NULL, **not first nonblank**

COALESCE(work_phone, mobile, email, 'no contact') returns an empty work_phone string if it is present. If the business wants the **first usable nonblank** contact, normalize each field first:

```sql
SELECT id,
       COALESCE(
         NULLIF(TRIM(work_phone), ''),
         NULLIF(TRIM(mobile), ''),
         NULLIF(TRIM(email), ''),
         'no contact'
       ) AS contact
FROM customer_contacts
ORDER BY id;
```

A local SQLite check with blank work phone, a later valid email, a valid mobile and all-missing values returned **(1, aa@a), (2, 555), (3, no contact)**. The source task uses a **customer_contacts** table missing from its shared seven-table schema; this rule is a transparent *additional assumption*, not a recovered official schema.

### A094 — NULL-safe joins may multiply matches

Ordinary SQL equality does **not** match NULL to NULL. When the source *explicitly* requires two unknown keys to match, use a NULL-safe predicate; **never assume a missing batch code is unique**:

```sql
SELECT s.id, t.id
FROM stage AS s
JOIN target AS t
  ON s.batch_code = t.batch_code
  OR (s.batch_code IS NULL AND t.batch_code IS NULL)
ORDER BY s.id, t.id;
```

Reviewer fixture: two NULL batch codes in stage and two in target yield **four** NULL-key pairs, plus one matching A/A pair. This is a possible fan-out, not necessarily a correct business match. The advanced PDF's **stage** and **target** relations are missing from the shared seven-table schema.

### P024 — one record can have **multiple** missing-data issues

Supplier review should preserve *all* qualifying problems. A foreign supplier with no email has **Outside India; No email**; a missing country and missing email require two labels too. A whitespace-only email is effectively blank only **when you explicitly apply TRIM**. Country case/whitespace normalization is not fully specified by the source and should not be invented.
