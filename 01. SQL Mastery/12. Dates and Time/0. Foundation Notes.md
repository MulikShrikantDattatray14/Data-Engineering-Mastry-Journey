# SQL Dates and Time — Foundation Notes

## Why learn dates carefully?

An order can happen on January 31 in UTC but February 1 in India. Incorrect date boundaries produce incorrect financial reports and break scheduled ETL partitions.

## 1. Half-open intervals

For all orders in January 2025:

```sql
SELECT order_id, placed_at
FROM Orders
WHERE placed_at >= '2025-01-01'
  AND placed_at < '2025-02-01';
```

```text
Jan 1 00:00                  Feb 1 00:00
|===========================|
Start INCLUDED                 End EXCLUDED
```

The final January day is included regardless of time of day; February 1 is excluded. Avoid treating a date like January 31 as though it automatically includes every timestamp on that date.

## 2. Group orders by month

**SQLite** with consistently formatted ISO dates:

```sql
SELECT strftime('%Y-%m', placed_at) AS month,
       COUNT(*) AS orders
FROM Orders
GROUP BY strftime('%Y-%m', placed_at)
ORDER BY month;
```

**SQL Server:** `DATEFROMPARTS(YEAR(placed_at), MONTH(placed_at), 1)` creates a typed first-of-month date key. Use query patterns matching the specific engine.

## 3. Time zone example

```text
UTC:    2025-01-31 20:00
India:  2025-02-01 01:30
```

That event belongs to **February** for an India-local reporting calendar. Use timezone-aware conversion for relevant geographies; not all zones have fixed offsets all year.

## 4. Common traps

- Use `>= start AND < next_start` to avoid missing events near midnight.
- Keep UTC timestamps consistent at storage boundaries; define the reporting timezone separately.
- Compare date/timestamp values, not arbitrary localized strings.
- Verify leap days, daylight-saving changes, missing timestamps and duplicates.
- Apply filters on indexed timestamps when possible, rather than wrapping every row in a conversion function.

**JavaScript comparison:** Similar concerns apply when converting a JS `Date` UTC timestamp to a locale-specific reporting day. SQL dialects provide different date/time operators.

## 5. Make date predicates index-friendly (PNP A096)

An ordinary B-tree index on \`order_date\` can be used more directly when the column is compared to a **computed constant** rather than transformed for every row. PNP A096 supplies \`DATEDIFF(CURDATE(), order_date) <= 30\`; rearranging this means:

\`\`\`sql
-- SQLite, with a fixed, testable report date:
SELECT id
FROM orders
WHERE order_date >= date('2026-02-01', '-30 days');
\`\`\`

The synthetic test verifies that SQLite's query plan uses \`idx_order_date\` and that January 2 is included while January 1 is not. **Important contradiction:** the supplied source expression also admits **future-dated orders**, because negative \`DATEDIFF\` values satisfy \`<=30\`. Adding \`AND order_date <= today\` is a sensible "last 30 days" business requirement, but is **not an equivalent rewrite** until that extra restriction is approved. SQLite \`date\` syntax is not MySQL \`DATE_SUB\` syntax; verify the engine-specific query separately.

## 6. Calendar weeks and missing months (A098, P064)

Sunday is weekday 0 in SQLite. To assign every date to its **Monday** of that week, shift backwards by \`(weekday + 6) % 7\` days. The archived A098 illustration intentionally crosses a year boundary: Sunday **2026-01-04** belongs to the week beginning **2025-12-29**. Do not group solely on bare week numbers or assume ISO-week/year formatting is identical across SQL dialects.

For P064's rolling three-**calendar-month** order average, first build a **calendar month spine** from minimum to maximum order date, then \`LEFT JOIN\` the monthly totals and turn absent months into zero. Only after filling gaps may \`AVG(...) OVER (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)\` represent three consecutive calendar months. The first **two** rows' three-month averages must remain NULL.

The archived illustrative totals **Jan=100, Feb=0, Mar=300, Apr=100** give **March=133.33** and **April=133.33**; these are independently asserted in [the date fixtures](../../scripts/check_pnp_dates_cases.py). An ordinary window on the source's *nonempty* months would incorrectly skip February.

## 7. First-order cohorts, observation maturity and look-back order (A099/A100, P061/P075/P076/P091)

**Choose the unit of analysis before computing anything.** An *order* is not a *customer*, and the first order per customer is not the first order **within a report window**. For A100, count each customer at most once if they order during the **next calendar month** after their first-order month, even if they have multiple return orders. A return after 30 days might fall in a different month, so "month one" cannot be modeled as simply 30 days.

P076 separates new-versus-returning **order value** for the last 12 months but must calculate each customer's first-order month using **all available history before the report restriction**. Otherwise an older customer reappearing during the window is incorrectly labeled new.

P061 (m1/m2/m3/m6 cohort retention) and P091 (cumulative cohort value at m0/m3/m6/m12) require an **observation-maturity rule**: a cohort that has not yet reached a report month should show NULL, not zero. A maximum observed order date is only a *proxy* for full source-data coverage; do not silently treat a partially observed last month as complete. P091's quarter cohort can contain customers acquired in three different months, so maturities may differ **within a quarter**.

For P075, an inclusive seven-day look-back ending on \`week_end\` starts at **\`week_end - 6 days\`**; an inclusive 28-day look-back starts at **\`week_end - 27 days\`**. Count **distinct customers**, not orders. Source prose says weekly reporting "every Monday," but its explicit instruction anchors each generated report date at the last *order date*, which need not be Monday. This remains an unresolved source contract.

## 8. Order-of-operations for return dates and leap-year comparison (P081/P085)

P085 needs \`LAG(OrderDate)\` over **all prior orders** for each customer **before** filtering return events to the reporting period. Filtering the report period first can erase an earlier order and hide a legitimate **180-day** win-back. Include exactly 180 days (\`>=180\`), and decide the ordering for same-day order ties when dates include only days.

P081 uses the latest observed date as the YTD comparison anchor. **February 29, 2024** must be compared with the prior year through **February 28, 2023**, not March 1. The independent fixture tests current value **300**, prior value **100** and excludes a March 1 prior-year order. Date arithmetic like "subtract one year" is engine-specific around leap days; express the Feb 29 policy explicitly.
