# SQL Data Quality and Deduplication — Foundation Notes

## Why this matters

An ingestion job retries a message. Now the warehouse sees two records with the **same business ID**. A dashboard might double-count sales unless we choose one valid version. Deduplication is not simply `DISTINCT`: two records can share the same order ID but have different timestamps or corrected amounts.

**Rule:** Define the **grain** and a deterministic rule for which version wins.

## 1. Sample raw data

| ingestion_id | order_id | updated_at | status | amount |
|---:|---:|---|---|---:|
| 1 | 101 | 2025-03-01 10:00 | PAID | 100 |
| 2 | 101 | 2025-03-01 11:00 | paid | 120 |
| 3 | 102 | 2025-03-02 09:00 | failed | -5 |
| 4 | 103 | 2025-03-02 10:00 | " paid " | 200 |

**Goal:** One latest version per `order_id`, then separate valid and invalid records.

## 2. Visual: rank duplicates

```text
Order 101
  10:00 → 100 → rn=2 (old)
  11:00 → 120 → rn=1 (keep)
Order 102
  09:00 → -5  → rn=1 (latest, but invalid)
Order 103
  10:00 → 200 → rn=1 (valid after trim/lower)
```

## 3. Rank one latest version per business key

```sql
WITH ranked AS (
  SELECT ingestion_id, order_id, updated_at, status, amount,
         ROW_NUMBER() OVER (
           PARTITION BY order_id
           ORDER BY updated_at DESC, ingestion_id DESC
         ) AS rn
  FROM RawOrders
)
SELECT order_id, status, amount
FROM ranked
WHERE rn = 1
ORDER BY order_id;
```

| order_id | status | amount |
|---:|---|---:|
| 101 | paid | 120 |
| 102 | failed | -5 |
| 103 | " paid " | 200 |

The `ingestion_id` tie-breaker makes equal-timestamp ranking deterministic. Never silently use `MAX(amount)` as a replacement for choosing the newest record.

## 4. Validate **after** selecting the latest version

```sql
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY order_id ORDER BY updated_at DESC, ingestion_id DESC
  ) AS rn
  FROM RawOrders
),
latest AS (
  SELECT order_id, lower(trim(status)) AS clean_status, amount
  FROM ranked
  WHERE rn = 1
)
SELECT order_id, clean_status, amount
FROM latest
WHERE clean_status = 'paid' AND amount >= 0
ORDER BY order_id;
```

**Valid output**

| order_id | clean_status | amount |
|---:|---|---:|
| 101 | paid | 120 |
| 103 | paid | 200 |

The latest 102 fails the nonnegative amount rule and should be **quarantined for review**, not quietly dropped without any record of its failure. Keep invalid rows in an error or quarantine table in real pipelines.

**Why order matters:** Validating before ranking could select an older valid version even if the newest record is invalid, hiding a current data-quality issue.

## 5. Common Data Engineering quality dimensions

| Check | Example |
|---|---|
| Completeness | Required order ID is non-NULL |
| Uniqueness | One current row per order ID |
| Validity | Amount >= 0; allowed status values |
| Consistency | Customer references an existing customer |
| Freshness | Last successful ingestion time is within SLA |
| Accuracy | Totals reconcile against a trusted source |

## SQLite / SQL Server / JS comparison

The `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` approach works in SQLite and SQL Server. String `trim/lower` syntax and data types differ across dialects; validate on the target DB. In JavaScript this is similar to sorting versions per `orderId`, keeping the first record in a Map, then applying validation—but SQL computes the partition ranking in one query.

## Revision

- `DISTINCT` removes identical projected rows; it does **not** choose the latest record for a key.
- Always order duplicates with deterministic tie-breakers.
- Do not mix business keys with ingestion event IDs.
- Bad data must be visible to operations; silent filtering is not a complete data-quality process.
