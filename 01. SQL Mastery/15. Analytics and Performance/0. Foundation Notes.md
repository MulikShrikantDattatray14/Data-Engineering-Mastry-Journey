# SQL Analytics and Performance — Foundation Notes

## Why this matters

A product team asks: **Which category contributes the most revenue, and what percentage of the business does it represent?** The answer needs correct grouping, a denominator across *all* groups, careful join grain and a query that scales.

## 1. Small dataset — one sale per row

| sale_id | category | amount |
|---:|---|---:|
| 1 | Home | 200 |
| 2 | Home | 100 |
| 3 | Books | 100 |

The business has **400 total revenue**. Home contributes 300; Books contributes 100.

## 2. Aggregate first, calculate the percentage

**SQLite SQL:**

```sql
WITH category_revenue AS (
  SELECT category, SUM(amount) AS revenue
  FROM Sales
  GROUP BY category
)
SELECT category, revenue,
       ROUND(100.0 * revenue / SUM(revenue) OVER (), 1) AS pct_total
FROM category_revenue
ORDER BY revenue DESC, category;
```

### Progressive result tables

**Step A — group:** `Home: 200 + 100 = 300`, `Books: 100`.

| category | revenue |
|---|---:|
| Home | 300 |
| Books | 100 |

**Step B — denominator:** `SUM(revenue) OVER () = 400` for each output row.

**Step C — ratio:** `100.0 × group_revenue ÷ all_revenue`.

| category | revenue | pct_total |
|---|---:|---:|
| Home | 300 | 75.0 |
| Books | 100 | 25.0 |

`100.0` makes decimal arithmetic explicit. For the empty/zero-total case, use `NULLIF(SUM(revenue) OVER (),0)` to avoid dividing by zero and decide how the business wants missing percentages reported.

## 3. Why query performance matters

Two correct SQL queries can have different costs. An index can help locate filtering rows, but building or maintaining an index has a cost. A query plan explains *how the engine plans to execute* the query; logical SQL is not necessarily executed in the order we write it.

```sql
-- SQLite: inspect a plan in a scratch database
EXPLAIN QUERY PLAN
SELECT * FROM Sales
WHERE category = 'Home';
```

**SQL Server** offers an execution plan and tools like `SET STATISTICS IO ON`; its plan vocabulary and index behavior differ. Don't assume a plan from SQLite predicts SQL Server performance.

## 4. Avoid aggregation after join fan-out

Imagine an order worth ₹500 has three line items. Joining Orders to OrderItems makes three rows carrying the same order amount. Summing `Orders.amount` *after* that join incorrectly produces ₹1,500.

**Correct reasoning:** Identify the grain of each source, then either aggregate/order-deduplicate before joining or sum the appropriately granular item values.

```text
Order 101 amount 500
        ↓ JOIN with three OrderItems rows
101 500
101 500
101 500
        ↓ naive SUM(order_amount)
1500   ❌ duplicated
```


## Extra PNP ratings: denominator, product grain, and limitations

The five preserved [product-ratings extra tasks](../PNP-SEMANTIC-AUDIT.md) are **not supplied with an official answer key**; their source illustrations and independently authored synthetic fixtures are not learner solves.

- **X002 — sample-size filter:** HAVING COUNT(Rating) >= 20 counts only rated products, whereas COUNT(*) includes unrated rows. AVG(Rating) ignores NULL, so use the *same population* in the mean and the threshold. Even a 20-rating threshold does not by itself guarantee representative reviews.
- **X003 — median units:** sum OrderDetails.Quantity per ProductID **before** taking a sub-category median. Source does not resolve whether products with zero observed sales belong in the median or how even-length medians should be treated. A reviewer should not silently choose.
- **X004 — comparison across rating bands:** average **product totals**, not order-detail lines. A product with many detail rows must still count as one product; in the source's example, a no-sale product counts as zero. The published labels overlap at 4; the illustration clarifies that 4.0 belongs to the top band (3 <= Rating < 4 is middle).
- **X005 — rated but never ordered:** an anti-join flags a provenance question, **not necessarily a bad rating**. Ratings may have originated before the order history or from another system.

One independently tested SQLite skeleton for the core X004 product-grain step:

```sql
SELECT p.ProductID,
       p.Rating,
       COALESCE(SUM(d.Quantity), 0) AS units_sold
FROM Products AS p
LEFT JOIN OrderDetails AS d ON d.ProductID = p.ProductID
GROUP BY p.ProductID, p.Rating;
```

Apply band labels and AVG(units_sold) **after** this per-product result, not directly to OrderDetails. The auditor's separate fixtures for X002, X004 and X005 passed; X003 was statement-inspected only. No source official-answer or learner-mastered status is inferred.

## 5. Performance and correctness checklist

- Does every output row represent what the question asks?
- Are `NULL` amounts included or skipped by an aggregate?
- Is the percentage denominator based on all relevant groups or just the filtered subset?
- Are tie-breakers deterministic for `TOP`/`LIMIT` queries?
- Can a filter use an existing index? Are functions applied to indexed columns unnecessarily?
- For large data, inspect the query plan and row counts before concluding a query is efficient.
- Avoid `SELECT *` and repeated expensive calculations when only some fields are needed.

**JavaScript connection:** SQL grouping is similar to reducing an array into a `Map<category,total>`. A window function adds a statistic over the full set without collapsing the group results.
