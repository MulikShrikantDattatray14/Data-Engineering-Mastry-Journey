## Contract and synthetic-data checks

Original task: among active categories, calculate every sub-category's units in the six months through the **latest OrderDate**, including zero-selling products in the denominator; compare against a **continuous P25** within the category and emit only strictly below-threshold sub-categories, ordered by category/units/sub-category. The original illustrative four sub-categories produce `Care/A`, one listing, zero units, `0.00` units per product, `7.50` P25. Native reviewer also covers exclusive six-month starting boundary, end-date inclusion, inactive-category exclusion, repeated detail lines, no-order population, non-selling product listing count and NULL quantity/sub-category.

**Conditional category-identity discrepancy:** original SQL groups sub-categories by `cat.CategoryName, p.Sub_Category` and thresholds by `CategoryName` instead of stable `CategoryID`. With two active categories, *different IDs but both named Care*, category 1's zero-selling A is combined with category 2's A selling 100 units. Native reviewer expects the unchanged supplier SQL to return only **Care/B (10 units per product, P25 17.50)**, whereas ID-specific analysis identifies Care/category-1/A as the bottom-ranked sub-category. This is a **conditional data-contract mismatch**, not evidence that the Commerce CSV has duplicate names or that the provider marked an answer incorrect.

**Conditional NULL-name exclusion:** an active category with NULL `CategoryName` can be grouped by NULL in both source CTEs, but `JOIN thresholds t ON t.CategoryName = s.CategoryName` cannot join NULL to NULL, so no underperforming row survives. The task has no independently established policy excluding nameless active categories. Again, **no actual population count is available**. These two issues were already described or implied in earlier compatible SQLite checks; native verification, if passing, strengthens engine confidence rather than adding new unique source-key coverage.
