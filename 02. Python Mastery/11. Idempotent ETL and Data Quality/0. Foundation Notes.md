# Idempotent ETL and Data Quality — Foundation Notes

## Why do we need this?

Your pipeline loads yesterday's orders. The scheduler retries the job after a network error. Without safeguards, the same orders may be loaded **twice**, corrupting revenue reports.

An **idempotent load** gives the **same intended final destination state** when rerun with the same source data. This is one of the most valuable engineering habits to learn early.

## 1. Visual flow

```text
SOURCE → EXTRACT → VALIDATE → TRANSFORM → LOAD → CHECK
CSV       read      IDs, dates     clean       upsert     row counts
                    amounts        status     /replace  and totals

Same input run twice → same intended final table (no duplicate orders)
```

## 2. Simple SQLite safe-load pattern

```python
import sqlite3

orders = [(101, 100), (102, 200)]
with sqlite3.connect(":memory:") as conn:
    conn.execute("CREATE TABLE orders(order_id INTEGER PRIMARY KEY, amount INTEGER)")
    def load(rows):
        with conn:
            conn.executemany(
                "INSERT INTO orders(order_id,amount) VALUES (?,?) "
                "ON CONFLICT(order_id) DO UPDATE SET amount=excluded.amount",
                rows,
            )
    load(orders)
    load(orders)
    print(conn.execute("SELECT COUNT(*), SUM(amount) FROM orders").fetchone())
# (2, 300)
```

**Progressive state**

| Action | IDs in target | Row count | Sum |
|---|---|---:|---:|
| Start | — | 0 | 0 |
| First load | 101, 102 | 2 | 300 |
| Retry same load | 101, 102 | 2 | 300 |

The primary key prevents duplicate order IDs; the upsert changes existing amounts to the source values. In real systems, idempotence also depends on event versioning, partitions, deletes, transactional boundaries and consistent replay inputs.

## 3. Validate before loading

For a business rule `amount > 0`:

- Reject or quarantine malformed amounts; don't silently turn them into zero.
- Check required identifiers and unexpected duplicate keys.
- Verify source vs target row counts and key uniqueness.
- Track batch ID, source checksum, status and any rejected records.
- Ensure a partial failure doesn't leave the destination half updated.

## 4. Testing differs from data quality

- **Unit tests:** check your transformation code against known inputs.
- **Data quality checks:** check each real batch before publishing it.
- **Integration tests:** verify that extract, transform and database load work together.

**JS analogy:** An idempotent API `PUT` operation aims to leave the same resource state on retry. A batch upsert has a similar intention, though distributed-system guarantees require more than just an API verb.

## Revision

**Reliable pipeline = correct business logic + replay safety + observability + data validation + failure recovery.** No data engineer can trust a metric solely because the script exited without an exception.

## Archived source review: secure queries, transactional replay and testing (PDF pp. 71–73; 2026-11-09)

**Parameterized SQL:** use `cursor.execute("SELECT ... WHERE status = ?", (status,))` with SQLite; never construct SQL predicates by interpolating untrusted input using f-strings. In the source, an intentionally unsafe status predicate can match all 15 demo orders, while the parameterized query correctly matches zero for the same hostile text. Use the parameter-marker style required by your driver.

**Atomic reruns:** for a date-partition replacement load, perform the old-day delete and new-day inserts within the **same database transaction**, so a failed insert rolls back the deletion. The source uses separate `extract`, `transform`, `load` stages and checks that rerunning the same day's input does not double the count. Rerun safety depends on deterministic source reads, primary keys, versioning and transaction boundaries—not merely on successful script exits.

**Unit tests vs data quality:** unit tests verify transform behavior on known input (including invalid rows), whereas data-quality rules examine real data **on every run**. Useful assertions: required IDs not null, amounts positive according to the business contract, ID uniqueness, expected status values, source-target count/revenue reconciliation, and an explicit quarantine count. Use `pytest.raises` to test rejected inputs, and `pytest.mark.parametrize` to cover multiple cases.

**Money caveat:** an introductory source uses `round(float(...), 2)`. For exact production currency, prefer `Decimal` with an agreed rounding mode. A retry after a commit is especially risky if your write is not idempotent.
