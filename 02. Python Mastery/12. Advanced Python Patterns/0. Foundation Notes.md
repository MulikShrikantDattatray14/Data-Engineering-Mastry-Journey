## 1. Lazy iterators and generators (PDF p. 35)

A large ETL job may have millions of records. A generator yields one item at a time when downstream code asks for it, rather than building another whole list.

```python
def valid_amounts(rows):
    for amount in rows:
        if amount > 0:
            yield amount

gen = valid_amounts([100, -5, 200])
print(next(gen))  # 100
print(list(gen))  # [200]
print(list(gen))  # [] — consumed already
```

**Data flow:** source row → generator filter → aggregation → result. `yield from other_iterable` delegates yielded values, and `next(iterator, default)` avoids a `StopIteration` when a stream is exhausted. A generator may still **retain references to a large input object**; its small object size is not proof that the whole pipeline uses little RAM.

**JavaScript link:** `function* f(){ yield x }` corresponds roughly to Python `def f(): yield x`. This does not turn blocking work into asynchronous I/O.

## 2. Why `itertools.groupby` is not SQL GROUP BY (PDF p. 36)

Python `groupby` creates a new group each time the **adjacent** key changes. SQL `GROUP BY` conceptually groups all records of a given key, regardless of original adjacency.

```python
from itertools import groupby

status = ["delivered", "cancelled", "delivered", "delivered"]
runs = [(key, len(list(g))) for key, g in groupby(status)]
print(runs)  # [('delivered', 1), ('cancelled', 1), ('delivered', 2)]
```

If you want one group per status, first **sort by the same key** (or use a dictionary accumulator). Sorting changes input ordering and costs O(n log n), which may be unnecessary for streaming frequency counts.

Useful tools: `islice` takes a slice of an iterator, `chain` joins streams lazily, `accumulate` provides running totals, and `pairwise` creates adjacent pairs. `itertools.batched` is built in starting with Python 3.12; check your runtime before using it. `functools.partial` presets arguments; `functools.reduce` folds an iterable; `heapq.nlargest` can find top-k items without sorting the whole input. Stable sorting makes multi-key sorting practical: sort by secondary key first, then by primary key.

## 3. Classes and dataclasses (PDF p. 37)

Use a class when an object has **behavior, validation, or an interface**, not merely because a record has fields. A dataclass generates the repetitive initializer and representation methods.

```python
from dataclasses import dataclass
from decimal import Decimal

@dataclass(frozen=True, slots=True)
class Order:
    order_id: int
    amount: Decimal
    def __post_init__(self):
        if self.amount <= 0:
            raise ValueError("amount must be positive")

print(Order(101, Decimal("1198.00")))
```

- `@dataclass(frozen=True)` prevents normal attribute reassignment; nested mutable objects can still change.
- `slots=True` can reduce per-instance memory and prevent arbitrary new attributes.
- `@classmethod` can construct objects from CSV string fields, validating types.
- `ABC` and `@abstractmethod` define a shared extractor interface, such as `rows()` for both CSV and JSON Lines. Prefer simple functions until multiple implementations genuinely benefit from an interface.

**JS comparison:** `class Order { constructor(...) ... }` is the nearest syntax analogy; dataclasses add auto-generated methods and optional immutability conventions.

## 4. Decorators and safe retrying (PDF p. 38)

A decorator returns a wrapper around another function. `@timed` means `load = timed(load)`. Use `functools.wraps` to retain the decorated function's name/docstring.

```python
from functools import wraps

def count_calls(fn):
    @wraps(fn)
    def wrapper(*args, **kwargs):
        wrapper.calls += 1
        return fn(*args, **kwargs)
    wrapper.calls = 0
    return wrapper

@count_calls
def batch_size(batch):
    return len(batch)

print(batch_size([1, 2]), batch_size.calls)  # 2 1
```

Only retry **transient errors** such as temporary connection failures. Never retry invalid input. Use a finite attempt limit, exponential backoff where appropriate, and consider server-specified rate limits. Retrying a write can duplicate side effects unless the operation has an idempotency key or transactional protection.

`@contextmanager` uses code before `yield` for setup and `finally` for cleanup. `with` blocks ensure cleanup even on failure; this is useful for files, database connections, and temporary resources.

## 5. Threads, processes and async I/O (PDF p. 39)

| Approach | Best fit | Pitfall |
|---|---|---|
| `ThreadPoolExecutor` | Independent requests waiting on network/disk | Race conditions on shared mutable state |
| `ProcessPoolExecutor` | Substantial CPU-bound independent computation | Startup/pickling/data-transfer overhead |
| `asyncio` | High numbers of waits using async-aware libraries | Blocking calls freeze the event loop |

`executor.map` returns outputs in *input order*, even if tasks finish out of order. Process worker functions must be serializable, and spawn-based platforms commonly require the `if __name__ == "__main__":` guard. On typical GIL-enabled CPython, threads are good at overlapping I/O but may not accelerate pure Python CPU loops; Python runtime builds differ, so benchmark rather than asserting absolute speedups.

```python
import asyncio

async def fetch_mock(page):
    await asyncio.sleep(0)  # yield control; no actual request
    return page * 100

async def main():
    return await asyncio.gather(*(fetch_mock(i) for i in (1, 2, 3)))

print(asyncio.run(main()))  # [100, 200, 300]
```

Async programming is about cooperative waits, not an automatic substitute for database transactions or CPU parallelism.
