## 1. Classes, objects and method types

A class defines behavior; each instance can store its own state. A **class attribute** is shared by default, whereas an **instance attribute** belongs to one object.

```python
class Extractor:
    kind = "CSV"  # class attribute

    def __init__(self, path):
        self.path = path  # instance attribute

    def description(self):  # instance method receives self
        return f"{self.kind}:{self.path}"

    @classmethod
    def from_config(cls, config):  # receives the class
        return cls(config["path"])

    @staticmethod
    def valid_name(name):  # receives neither self nor cls automatically
        return name.endswith(".csv")

obj = Extractor.from_config({"path": "orders.csv"})
print(obj.description(), Extractor.valid_name(obj.path))
# CSV:orders.csv True
```

Python class methods require the **`@classmethod` decorator**; an ordinary method in a class is not automatically a class method. A shared mutable class attribute such as `items = []` can unexpectedly mix records from multiple instances; allocate per-instance lists in `__init__`.

## 2. Inheritance, overriding and super

A subclass extends an existing interface. Inheritance can be single, multilevel, hierarchical or multiple; use composition when a class needs a tool rather than meaningfully *being* a subtype. An overridden method replaces inherited behavior for that instance.

```python
class BaseLoader:
    def __init__(self):
        self.calls = 0
    def load(self, rows):
        self.calls += 1
        return len(rows)

class ValidatingLoader(BaseLoader):
    def load(self, rows):
        if any(row is None for row in rows):
            raise ValueError("null row")
        return super().load(rows)

loader = ValidatingLoader()
print(loader.load([1, 2]), loader.calls)  # 2 1
```

`super()` participates in Python's method-resolution order (MRO), rather than necessarily meaning a single named parent. In diamond-shaped multiple inheritance, `Class.__mro__` shows the C3 linearization. Classes should cooperate through consistent `super()` patterns when multiple inheritance is intentional.

## 3. Encapsulation and name mangling

Python's `_helper` is a convention meaning *internal use*; it is **not access protection**. A double-leading-underscore field such as `self.__token` is name-mangled to reduce accidental name collisions, not to keep secrets safe. Real credentials should never be committed to course examples.

Use `@property` when a public attribute needs validation or computed behavior:

```python
class Batch:
    def __init__(self, size):
        self.size = size

    @property
    def size(self):
        return self._size

    @size.setter
    def size(self, value):
        if value <= 0:
            raise ValueError("size must be positive")
        self._size = value

print(Batch(10).size)  # 10
```

## 4. Polymorphism, duck typing and operator methods

**Polymorphism** means a caller can use a common operation across different implementations. Python often uses *duck typing*: a function can accept any object offering the required method, without forcing unrelated subclasses.

```python
def count_rows(source):
    return sum(1 for _ in source.rows())
```

This can work for a `CsvExtractor`, `JsonlExtractor`, or test double that implements `rows()`. For explicit contracts, `abc.ABC` with `@abstractmethod` or a typing `Protocol` is useful. Special methods such as `__len__` and `__add__` control operations; operator overloading should match expected semantics, not surprise readers.

## 5. Dataclasses and realistic pipeline choice

A `@dataclass` makes a typed record less repetitive, while `frozen=True` prevents simple field rebinding and `slots=True` may reduce overhead. These do not imply that nested mutable data becomes deep-immutable. Use **dataclasses for typed records**, **small functions for simple transformations**, and **classes for genuine stateful or substitutable components**.
